## 背景与目标

需求建立时，主要 workspace 使用 Cargo 平台配置构建，默认产物在 `target/`；独立 `qf-gen-dyn0` 工程说明使用独立 `target/release/`。当时仓库已有 `scripts/install-bin.sh`，能将扁平的八个主二进制整理为家族目录，并可附加安装 dyn0 工具；根 README 已记录该分组布局。Linux musl 构建产物在 `dist/.../bin`，EPW 测试运行目录存在最终程序副本。当前实施结果另见 [验收记录](acceptance.md)。

目标是统一 DFTFlow 对外可运行程序的仓库内构建位置和分组契约，使受支持构建产物都可从根 `bin/` 找到，不再把交付程序保存在算例/测试目录，并让安装、打包和测试脚本直接消费该契约。

### 需求结论与变更取舍

纳入用户最新确认的边界：只整理 DFTFlow 自身交付程序。最终程序按家族放在 `bin/<family>/`；Cargo 编译缓存及测试 harness 可留在 `bin/.build/` 等专用区，不作为家族产品。测试目录允许输入、日志和结果，不保存 DFTFlow 可交付二进制。外部 QE/VASP/Wannier90 求解器不属于 DFTFlow 构建产物。

现有 `install-bin.sh` 已提供分组复制、启动核验和失败保护，Plan 以复用为主；采用用户最新要求：仓库模块目录是唯一日常程序来源，交付构建成功前自动完成必要兼容准备和发布；迁移依赖及活动引用后完整删除旧用户安装目录。Linux 发布包保留发行格式，来源绑定本次制品。

按后续追加要求提供 `PATH` 配置：shell 不递归搜索子目录，因此要加入七个家族目录，而非仅根 `bin/`。使用绝对路径，在任意工作目录都能按命令名运行；构建缓存不加入命令搜索路径。

## 用户场景与验收

### US1：按家族查找构建程序（优先级：P1）

开发者完成仓库支持的构建后，能在根 `bin/` 对应家族目录中找到可直接运行的程序，无需到 Cargo 默认目录或测试算例目录寻找、复制。

**优先级理由**：这是用户明确提出的主要结果，且能独立验收。

**独立验收**：执行构建入口后逐项检查家族路径、可执行权限和 `--help`；再次构建后路径集合稳定。

**验收场景**：

1. **假如** workspace 与独立工具依赖就绪，**当**运行相应构建入口，**那么**所有受支持 DFTFlow 交付程序都位于 `bin/<family>/`。
2. **假如** EPW 的三个阶段程序已构建，**当**检查交付目录，**那么**三个程序都在 `bin/epwflow/`。
3. **假如**构建已执行过一次，**当**再次构建相同目标，**那么**程序仍写入相同路径并覆盖旧内容，不产生新编号目录。

### US2：测试目录只存放测试数据与证据（优先级：P1）

开发者在编号算例目录运行脚本时，脚本从仓库规范 `bin/` 使用 DFTFlow 程序；算例目录不承担二进制仓库。

**优先级理由**：用户明确要求不再把程序放在 `test_auto` 计算目录。

**独立验收**：盘点受支持测试目录的 DFTFlow 可交付程序并核对活动引用；不存在依赖旧副本的通过路径。

**验收场景**：

1. **假如**测试算例目录有 DFTFlow 调用脚本，**当**从该目录按文档启动测试，**那么**脚本解析到根 `bin/<family>/` 中的程序。
2. **假如**测试路径存在历史 DFTFlow 二进制副本，**当**迁移完成，**那么**副本移出测试目录且脚本不再引用旧路径。

### US3：在任意目录直接使用命令（优先级：P1）

用户按说明配置 `PATH` 后，在仓库外也能通过 `epw_phonon`、`qeflow`、`qe_scf` 等命令名调用对应程序。

**优先级理由**：落实用户追加的任意位置调用要求。

**独立验收**：在干净 Bash/Zsh 子 shell 加载配置，切换到仓库外，检查命令解析位置及 `--help`；连续加载两次后 `PATH` 保持一致。

**验收场景**：

1. **假如**产品程序已位于家族目录，**当**加载配置并切换到仓库外目录，**那么**命令名解析到对应家族目录中的程序或兼容入口。
2. **假如**配置已经加载，**当**再次加载，**那么**不重复添加这些路径且原有系统路径保留。
3. **假如**用户希望新终端生效，**当**按说明将配置段添加到其 shell 启动文件并打开相应交互 shell，**那么**无需再次手动逐个设置路径。

## 边界与异常场景

- 未构建、缺失或不可执行的交付程序必须使安装/打包在改变现有安装内容前失败，并指出缺失家族和程序。
- 家族目录路径冲突为文件、链接或不可写时，构建/整理脚本应报告明确错误，不静默写入测试目录或扁平备用目录。
- Cargo 缓存和测试 harness 可存在于 `bin/` 下构建专用目录；它们不计入公开程序清单和家族程序数量。
- Linux `dist` 是发行包目录，不是仓库常规构建源目录；包中可继续使用发行格式，但来源必须绑定本次成功构建的根 `bin/` 程序。
- 重复发布覆盖仓库模块路径；退役会重建旧用户目录的固定安装入口，不保留第二套日常安装。
- `PATH` 中已有同名程序时，首次配置将新加入的仓库家族目录置于原有路径之前；使用 `command -v` 核对实际来源。后续重复加载不重复添加目录。
- shell alias/函数也可能影响命令解析；说明使用 `type -a` 排查，Bash 可用 `hash -r` 清空旧命令缓存。
- 当前 shell 的 `export` 只由该 shell 及其后代继承；新终端需加载启动文件，独立批处理作业仍按其环境加载配置或使用绝对路径。

## 功能需求

- **FR-001**：所有受支持的 DFTFlow 构建入口必须将仓库内 Cargo target/cache 输出置于根 `bin/` 内的构建专用区域；Linux 容器可使用专用挂载缓存，但不得将其作为仓库交付位置或写入算例目录。
- **FR-002**：本机构建完成后必须把可交付程序稳定整理到 `bin/epwflow/`、`bin/qeflow/`、`bin/substitutionflow/`、`bin/vaspflow/`、`bin/wannierflow/`、`bin/scflow/` 与 `bin/tools/`。交叉目标与 musl 发行包保留独立制品快照和发行目录，不替换宿主日常程序。
- **FR-003**：程序映射必须为：`epw_phonon`、`epw_wannier`、`epw_superconductivity`→`epwflow`；`qeflow`→`qeflow`；`substitution`→`substitutionflow`；`vaspflow`→`vaspflow`；`wannier90`→`wannierflow`；`scflow`→`scflow`；独立 `qf-gen-dyn0`→`tools`。
- **FR-004**：构建、分组发布、兼容入口与 Linux 打包脚本必须从本次成功构建的明确制品快照读取程序，不依赖测试目录副本；交付构建自动发布，兼容入口在模块内生成；退役旧固定安装入口。
- **FR-005**：仓库测试与验收脚本调用 DFTFlow 程序时必须从仓库根 `bin/` 解析路径；测试 harness、探针和临时工具不要求纳入产品家族目录。
- **FR-006**：已发现的测试目录 DFTFlow 交付程序副本必须迁出，相关脚本和手册路径同步更新；修改前核对活动 Slurm 作业、生成脚本和数据来源引用，保留运行结果及必要的历史证据。
- **FR-007**：`bin/` 作为本机生成产物目录继续被 Git 忽略；不提交本机可执行文件、Cargo 缓存或运行库。
- **FR-008**：支持重复构建覆盖稳定路径；编译、制品准备或启动预检失败不替换现有可用程序；不得退回算例目录。
- **FR-009**：提供将七个家族目录以绝对路径加入并导出 `PATH` 的 Bash/Zsh 配置示例，保留原有搜索路径；重复加载不重复添加目录，不加入 Cargo 构建缓存或测试目录。
- **FR-010**：说明当前 shell 生效、用户手动持久化与新终端加载的方法，并给出仓库外命令解析及帮助启动验证；不自动修改 shell 启动文件。

### US4：删除旧安装后仍能构建和运行（优先级：P1）

用户完整删除 `~/.local/share/dftflow/` 后，仍可在仓库构建、增量更新并启动九个产品。删除前迁移编译依赖、私有运行库与加载器，处理活动引用；冻结记录不改写。

**独立验收**：旧路径不可访问时构建与启动通过；清理自有旧入口后删除旧目录，再次构建和测试不重建它。

- **FR-011**：默认完整、按模块和独立工具交付构建成功返回前，必须自动完成制品准备及发布；仅发布 Cargo 本次报告的产品，不刷新未构建模块；测试、检查和库构建不发布 CLI。
- **FR-012**：将仍需使用的编译依赖、运行库、加载器及工具迁入仓库私有产物区，更新本机配置、元数据及 ELF 引用；公开 PATH 不暴露缓存和私有运行库。
- **FR-013**：保留计算节点兼容性；未完成目标环境所需打包的原始产物不能直接发布。
- **FR-014**：删除前核验活动进程、调度作业、脚本及恢复引用。完成迁移后完整删除旧根目录，不保留同名链接或空壳；清理旧自有入口，保留其他应用。
- **FR-015**：构建、打包、安装与工具操作不得重新创建旧根目录；缺失模块不得静默回退旧安装。
- **FR-016**：保留历史脚本、输出与回执；历史二进制可按原哈希迁往仓库私有归档并另记迁移清单，不修改冻结身份。仍需续算的工作区按已有新尝试或导入契约使用，不伪造历史身份。
- **FR-017**：同步根 README、Overview、模块及工具说明、测试指南与 0011 后续关系；保留线上 Gitee 用户自管边界。

## 成功标准

- **SC-001**：受支持 workspace 构建生成的八个主程序均位于其指定家族目录；独立工具构建生成 `bin/tools/qf-gen-dyn0`。所有清单项均可执行且 `--help` 成功。
- **SC-002**：根 `bin/` 下全部唯一可执行程序均属于明确产品清单；现有兼容命令软链接按家族归档；测试 harness/缓存若存在，只位于构建专用子目录。
- **SC-003**：受检查的 `test_auto` 目录没有 DFTFlow 交付二进制，所有活动脚本对程序的引用均解析至仓库 `bin/`。
- **SC-004**：workspace、独立工具及发布失败保护测试通过，兼容入口启动通过；Linux 发行链适配并验证，无法执行的平台检查明确记录未执行，不计通过。
- **SC-005**：连续两次构建的交付相对路径集合完全一致，程序更新后 SHA-256 对应当前构建，未产生按算例或时间新增的程序目录。
- **SC-006**：干净 Bash/Zsh shell 加载配置后，在仓库外目录可通过命令名运行九个产品程序和已安装兼容入口的 `--help`，`command -v` 指向规范家族目录。
- **SC-007**：相同配置连续加载两次，`PATH` 字符串不变且原有系统目录保留；文档给出对应 shell 的持久化与新终端生效说明。

- **SC-008**：完整 workspace 构建和独立工具构建后无需额外安装即可使用九个产品；EPW 按模块构建只发布三个目标，记录原始与发布后指纹。
- **SC-009**：编译失败、制品预检失败及非交付操作不改变现有产品；两次成功构建的公开路径集合稳定。
- **SC-010**：旧目录不可访问时，所需依赖、构建和九个产品启动通过，活动 ELF 与构建配置不再引用旧根。
- **SC-011**：活动引用逐项核验，绑定中的程序在使用期间不替换；冻结证据哈希保持，迁移归档可验证。
- **SC-012**：旧根目录完整删除，旧自有入口已清理；再次构建、测试和启动不重建该目录。
- **SC-013**：新环境在仓库外解析全部公开命令到模块目录；重复加载保持幂等，旧入口不遮挡。
- **SC-014**：本次需求、设计、任务和验收证据完整；不存在指向已删除需求目录的本地链接。
