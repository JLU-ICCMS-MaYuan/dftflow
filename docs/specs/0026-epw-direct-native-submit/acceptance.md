# 0026 实施与验收

## 已实现行为

编号工作区的三个公开程序通过 `-s` 在作业外校验上一任务、准备当前就绪任务并最多提交一次原生调用。实际脚本包含 Slurm 设置、环境加载、目录切换与一次 `exec`，直接调用 QE、Wannier90／postw90 或 EPW；没有 DFTFlow 准备、科学核验、记录或推进命令。

任务记录固定命令、输入、程序与来源身份、唯一脚本、预算回执、原生退出状态和日志。活动、未知及冲突状态阻止重复提交；明确失败后须 `--resume -s`。Slurm 正常结束仍须公开命令进行科学产物核验，零退出的无效产物不放行。

`--all` 只准备就绪脚本与 `native-plan.json`；状态查询只读。Tc 按模式、温度和初值逐次推进，暂停沿用原尝试和求解次数，继续使用原搜索与双初值判据。独立 W90 后处理在 `native-post/` 副本进行，保护拟合来源。

## 验证证据

公开进程及实际 shell 执行覆盖：

- 捕获真正的 `sbatch` 目标，执行原生替身，核对一次原生调用、零 DFTFlow 执行入口、工作目录及原生日志。
- 三个公开目标连续推进，检查上游成功任务不重复、两模式 Tc 完成以及最终调用不再提交。
- 并发控制、排队防重、未知回执保留预算、失败显式恢复、零退出无效输出拒绝、DOS 失败只重试失败任务。
- 环境加载失败保留退出码、程序及环境路径含空格、从其他目录执行脚本、手改脚本独立提交但不生成正式完成收据。
- 只读状态的运行／待核验／失败／已核验区分、准备清单零提交、脚本及输入身份冲突。

工作区存在其他任务修改，因此另从已提交基线构造只含本项补丁的隔离源码，单独编译并执行回归。首次连续检查发现 PH 重复归集及 dyn0 自复制问题，修正后完整原生链通过；其余阶段及既有科学回归分别复测，初次失败不计为通过。最终统计见下表。原生程序及调度器均为受控替身，没有新提交真实科学作业。

## 恢复路径修正

手动推进会反复进入原科学函数。QE 保存树与输入在继续归集时不再重新准备；多调用检查点逐个返回已登记的原生报告。PH 后处理重验已发布交付，避免重复创建保存目录；同时避免 `dyn0` 复制到自身被截断。Tc 的暂停不写成失败，也不重复扣减求解次数。

## 文档与兼容边界

Issue／Spec、Plan、Research、数据契约、Tasks、快速验证、模块 README 与 Overview 一起维护。旧式整阶段自动提交的测试由直接提交契约取代，保留科学解析、只读保护、原搜索算法与旧 `-r` 的回归。

实现继续复用既有输入生成、产物解析及 Tc 搜索，统一在外部程序执行边界记录和暂停；脚本生成与作业外推进各自承担明确职责。没有复制科学算法、新增公开程序或后台服务，保持单份脚本一次原生调用。

新提交面向 `layout='numbered'`。旧非编号布局的新 `-s` 明确提示显式迁移，不继续提交旧执行器包装脚本；历史冻结脚本、已有科学数据及默认安装不原地覆盖。线上 Gitee 由用户管理，本轮不操作线上 Issue、不推送、不切换分支；替身通过不代表新增真实科学验收。
