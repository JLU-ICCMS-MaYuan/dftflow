## 背景与目标

当前提交脚本通过内部参数转入 Rust 执行器，再由程序决定启动何种科学程序。即使能读到阶段名，用户也难以从脚本确认实际命令、输入、输出与执行顺序。目标是让 `-s` 提交的脚本本身成为可读的执行依据，方便核查和定位失败。

### 需求结论与变更取舍

直接科学调用适用于 EPW 管理链中实际需要的 QE、Wannier90 和 EPW 程序；独立 Wannier90 与 EPW 内置 Wannier 使用各自现有科学路径。不因“直接调用”新增一套科学算法或改变已经选定的程序。

0024 的日志与失败处理要求继续适用。本项解决科学调用被内部执行器隐藏的问题，不能以脚本更短或日志路径更短替代验收。

后来的四项选择明确改变初稿：作业内不保留 DFTFlow 辅助入口；后续由用户再次调用公开命令推进；手工脚本允许独立调试但不自动接入正式交付；`--all` 改为准备清单。这些行为替代原稿自动串联及未决调度描述，保留旧原话，不把原稿解释改写成用户曾经要求的内容。

一次 `-s` 的用户流程为：核验已结束任务并保存有效记录 → 准备下一任务 → 提交一次原生调用 → 立即返回。活动或未知任务阻止提交，失败任务须显式恢复；所有任务均完成时，仅报告完成，不新增作业。没有后台进程、长期等待或计算节点嵌套提交。

## 用户场景与验收

### US1（P1）：提交前后都能读懂实际执行命令

用户使用三个公开 EPW 入口的 `-s`，查看实际提交的作业脚本，能够确认相应可执行程序、参数、输入、输出及运行目录。

**优先级理由**：直接回应用户无法判断如何提交、难以 debug 的问题。

**独立验收**：通过公开 CLI 捕获真实调用的 `sbatch` 参数，读取目标脚本并执行受控原生替身，核对参数、目录、输入字节和输出位置。

1. **假如**需要 QE 计算，**当**执行相应公开入口的 `-s`，**那么**实际目标脚本直接包含所需 `pw.x`、`ph.x` 或相应后处理命令。
2. **假如**需要独立 Wannier90 或 EPW 计算，**当**提交对应任务，**那么**每份脚本直接包含该任务的一次 Wannier90／接口／后处理程序或 `epw.x` 调用，必要顺序由逐任务推进维护。
3. **假如**提交成功，**当**查看 CLI 输出，**那么**能获得任务、作业号、实际目标脚本路径和后续操作，不需要从内部 JSON 推导命令。
4. **假如**查看任一新实际作业脚本，**那么**除 Slurm 设置、环境加载、目录切换、必要失败判断和一次原生调用外，没有 DFTFlow 准备、核验、记录或推进命令。

### US2（P1）：debug 时能定位失败步骤并可靠恢复

用户从原生日志识别失败步骤，通过既有公开恢复操作生成新的直接调用脚本，相容的成功上游可复用。

**优先级理由**：可读性不能以失败后继续计算、重复消耗或错误复用为代价。

**独立验收**：注入环境、目录及原生计算失败，验证脚本退出；在作业外核验时注入无效结果，验证下游未提交、成功状态未发布，以及恢复复用与预算记录。

1. **假如**关键步骤失败，**当**脚本结束，**那么**失败可从退出结果及日志定位，后续依赖步骤不执行，不发布成功交付。
2. **假如**上游已相容完成，**当**恢复失败阶段，**那么**新的实际脚本只执行必要科学步骤，保留旧失败证据。
3. **假如**作业活动、提交结果未知或输入身份冲突，**当**再次提交，**那么**继续阻止重复执行或不相容复用。

### US3（P1）：由用户逐任务推进及搜索 Tc

用户在作业结束后再次调用同一目标的公开命令，让程序核验已有结果并提交下一项必要任务；目标完成时不额外提交。

**优先级理由**：这是用户选择的衔接方式，也是纯原生作业脚本的执行边界。

**独立验收**：从公开入口反复执行 `-s`，核对每次最多一个新作业；Tc 使用已知温度分类的受控原生输出，验证下一温度、第二初值、原次数上限和最终结果。

1. **假如**上一任务已结束，**当**再次调用 `-s`，**那么**先核验原生结果和来源，再准备及提交下一任务；命令不持续等待新作业。
2. **假如**缺少上游结果，**当**准备下一任务，**那么**不伪造输入、不将未就绪任务作为可提交任务。
3. **假如**需要 Tc 下一温度或第二初值，**当**再次调用公开入口，**那么**按原算法准备一次新求解；每份作业脚本仍只有一次 `epw.x` 调用。
4. **假如**最后一次求解已结束，**当**再次运行 `-s`，**那么**完成核验与结果发布，报告目标完成且不调用 `sbatch`。

### US4（P1）：准备清单与独立手工调试

用户通过 `--all` 查看当前可以准备的脚本和剩余步骤，也可修改脚本手工 `sbatch` 调试；程序明确区分调试结果与正式完成证据。

**优先级理由**：落实用户对总入口及手工 debug 的明确选择，避免旧一键串联用法误导。

**独立验收**：验证 `--all` 的输出、零提交和未就绪项；修改脚本后执行受控手工提交，核对正式记录不变和后续冲突拒绝。

1. **假如**部分依赖未完成，**当**执行 `epw_phonon --all`，**那么**只生成当前可准备的原生脚本及待完成步骤清单，不提交、不生成自动串联全流程的总脚本。
2. **假如**用户修改脚本并手工提交，**那么**可以独立调试，但不会自动生成正式完成收据；正式提交不接管修改过的脚本，恢复时重验来源和产物。

### 边界与异常场景

- 路径含空格时，可执行程序、输入、输出、环境加载与目录切换仍正确。
- SCF／NSCF 产物产生后才能决定的输入，必须在依赖可用后准备，不能为提前展示命令而伪造数据；真正启动程序的命令仍须出现在其实际提交脚本中。
- 数据复制、动态输入准备、质量核验与状态更新都在公开命令调用中完成，不在作业内执行，也不生成包含这些职责的二级 shell 执行器。
- 一份脚本只调用一次科学程序；科学失败的非零退出码直接成为作业退出码，不在脚本内串联后续计算或提交另一作业。
- 原生程序零退出但日志或必要产物不合格时，由下一次公开调用判为失败；核验前只表示已结束待核验，不能以 Slurm 提交成功或正常结束代替科学完成。
- 旧冻结脚本、已有尝试和预算记录不原地改写；新脚本与旧恢复证据的兼容边界在设计阶段明确。
- 手工修改脚本后独立 `sbatch` 不经过 DFTFlow 的提交预算登记；不能声称正式防重、预算登记或完成收据自动覆盖该作业。正式流程不自动接管或导入这些结果，身份或产物冲突必须报错；正式重试通过公开入口生成新尝试。
- `--status` 保持只读，区分运行中、已结束待核验、失败、已核验完成；不借查询触发结果接管、输入准备或下一作业。
- 对完成任务的核验和预算结算在显式公开调用中进行；账表未知时保留预留，不按脚本退出猜测计费。失败重试沿用原次数与累计消费。

## 需求

### 功能需求

- **FR-001**：三个公开入口的 `-s` 必须提交直接执行所需科学可执行程序的脚本，覆盖受支持的阶段选择及恢复路径；一次调用最多提交一个当前可运行任务并立即返回。
- **FR-002**：科学程序调用必须出现在实际被提交的脚本中，明确可执行程序、launcher、参数、目录、输入及输出；不得只生成另一个展示脚本。
- **FR-003**：实际作业脚本只包含 Slurm 设置、环境加载、目录切换及一次原生调用，允许环境和目录操作所需的最小失败判断；不得包含 `--workspace-attempt`、`--workspace-task` 或任何 DFTFlow 科学执行、准备、核验、记录、推进命令。
- **FR-004**：直接调用须沿用相应科学路径的程序和依赖顺序，覆盖实际需要的 QE、独立 Wannier90、接口／后处理及 EPW 程序；不强行互换独立与内置 Wannier 路径。
- **FR-005**：执行路径、资源和参数继续来自当前有效配置；不照搬参考脚本的机器硬编码、无关清理或调度系统扩展。
- **FR-006**：`-s` 提交成功必须报告任务、实际脚本路径、作业号及后续操作；科学日志与输入须可由该脚本定位。
- **FR-007**：关键环境准备、目录切换或科学执行失败时，脚本以非零结果结束；原生失败保留原始退出码。作业外核验不合格时报告失败，不提交下游、不发布成功交付；零退出的无效科学结果也不得放行。
- **FR-008**：运行身份与输入快照核验、预算预留和结算、活动／未知防重、相容复用及失败恢复由作业外公开命令负责，不再通过作业内辅助入口执行。脚本简化不授权取消这些管理约束，也不承诺作业内运行 DFTFlow 身份核验。
- **FR-009**：生成脚本遵循 0019 和 0024 的约束，不注入严格选项、不生成 `|| exit $?`；Slurm 日志只写文件名且保存在对应脚本目录，跨目录提交也需满足。
- **FR-010**：默认生成与 `-s` 使用同一原生脚本生成规则，仅准备依赖已可用的任务；历史冻结脚本与数据保持原样，不将旧包装脚本继续作为本项新提交路径。
- **FR-011**：用户再次调用公开 `-s` 时，先检查已提交任务的调度终态与原生结果，再更新有效记录、准备下一输入并提交下一任务；活动或未知状态拒绝重复，失败任务需显式恢复，全部完成时报告完成且不再提交。不新增长期等待、后台调度器或嵌套提交。
- **FR-012**：Tc 的每个模式、温度、初值各用一次独立原生调用；由后续公开调用准备下一温度、第二初值并分类，保持原搜索算法、求解次数上限、来源、科学标准及最终结果核验。
- **FR-013**：允许用户修改脚本并手工 `sbatch` 独立调试；手工结果不自动登记、导入或认作正式完成。正式提交不接管修改后的脚本，恢复时核验来源与产物，冲突明确报错，正式重试生成新尝试。
- **FR-014**：保留 `epw_phonon --all`，仅生成当前可准备的原生脚本及待完成步骤清单，不调用 `sbatch`、不生成自动全流程总提交脚本、不伪造依赖未满足时的输入。
- **FR-015**：状态查询保持只读并明确区分运行中、已结束待核验、失败和已核验完成；已结束任务须经显式公开调用核验后才获得正式完成记录。

### 关键实体

- **实际提交脚本**：`sbatch` 真正接收的脚本；只包含资源／环境／目录和一次原生调用，关联一次提交身份。
- **原生计算步骤**：某程序在指定目录读取指定输入并产生输出的执行单元；参数和来源应能核验。
- **提交与完成证据**：作业号、脚本身份、来源及原生结果核验记录；提交成功与科学完成分别判定。
- **准备清单**：当前可准备的原生脚本及因上游结果尚未可用而待完成的任务说明，不是自动提交入口。
