# 需求规格

## 原始需求记录

我建议取消数值检查的阻断阈值。保留数值校验逻辑，但当检测值超出预设理想阈值时，**仅做告警提示，不中断后续计算流程**。我希望对此新建一个 issue，然后继续往后测试，因为很有可能当前的数值检查超过阈值是因为你设置的参数不合理，但是不影响你往后进行，先把代码逻辑跑通了。

需求入口：[Issue](issue-draft.md)。无附件，images: []。

## 用户故事

US1：用户希望先跑通完整链，看到真实误差但不因理想误差阈值而停算。
US2：用户继续计算时仍需阻止损坏、不相容和不可解析的输入，输出不能混淆科学质量与执行完成。

## 功能需求

- FR-001：保留独立电子／声子误差、单位、最大／RMS 理想阈值和布尔达标结论；超差时打印明确告警及实际值／理想值，退出状态不因超差而失败。
- FR-002：粗网格发布、细网格启动／发布、超导启动／各尝试前、工作流验证及显式续算采用同一行为；质量摘要用 warning 区分超差和 valid，完整数据允许继续，不伪造原报告通过；最终交付的执行完成状态与数值质量分开，质量失败不能令已完成的流程返回失败。
- FR-003：原科学来源、哈希、格式、完整性、并行、预算及原生失败检查继续阻断；缺少独立参考不能视为数值告警。
- FR-004：已有成功 QE、PH、拟合、粗网格和比较结果通过重验后复用；冻结脚本与历史报告不改写。
- FR-005：规范构建安装后在指定 epwflow 目录继续真实细网格／超导测试，保留告警、作业及原生产物证据；协议验证和科学验收分开记录，不凭阈值告警推断参数合理。

## 成功标准

- SC-001：公开进程中电子／声子超差后粗网格发布 warning，下游实际进入细网格与两模式原生求解，数值报告 passed=false 和误差保持；合法达标情形仍通过。
- SC-002：缺失、篡改、非有限数或原生失败返回非零，未启动不合法下游；检查命令超差返回零并输出告警与真实结果。
- SC-003：安装源码身份一致；实际恢复不重复有效上游，记录真实细网格谱及求解结果，若遇新 Bug 建独立 Issue／Spec 修复；未达科学验收如实标记。
- SC-004：模块、本例、Overview 与本地需求相互链接，验证后仅范围提交，不推送。
