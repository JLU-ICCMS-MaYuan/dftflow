- **唯一类型**：`type:maintenance`。
- **编号约定**：0054 为本地暂定编号；沿用线上 Gitee 由用户管理的约定。
- **状态**：本地 Issue 与 Spec 草稿，供审查；不表示线上已创建、需求已实现或该版最终草案已获确认。
- **关联规格**：[spec.md](spec.md)；[现状调查](research.md)；[需求质量检查](checklists/requirements.md)。

## 原始需求记录

> 我不想再保留~/.local/share/dftflow/了，删除他吧。既然已经把/data/home/mayuan/code/dftflow/bin里面的各个目录都加到了环境变量里面，每次编译好之后，这些新的可执行文件就可以使用了。对不对。我记得提过这个需求。你是不是没找到。我建议把它变成一个 issue 和 spec 来做。

## 问题与目标

找到了已有的 [0017](../0017-build-binaries-layout/issue-draft.md)：按家族组织程序并提供 PATH 加载脚本已经有需求与部分实现，构建后自动整理程序的任务尚未完成。当前构建仍写入 `target/`，日常 `bin/` 不随构建自动更新；本次工具会话的默认命令还指向旧的用户安装。

2026-10-23 只读核验发现，仓库九个产品二进制的 ELF 加载器路径均位于 `~/.local/share/dftflow/native/`，本机编译配置也依赖该前缀。仅删除旧安装会破坏仓库程序的启动和后续构建。

目标是以 `/data/home/mayuan/code/dftflow/bin/<模块>/` 为本机唯一日常程序来源；受支持的交付构建入口在成功返回前自动完成必要打包和更新，用户无需再手动安装到第二个位置；迁移依赖、核验引用后完整删除 `~/.local/share/dftflow/`。

## 范围

- 覆盖全部 DFTFlow 自身产品：主 workspace 八个二进制、独立 `qf-gen-dyn0` 以及现有兼容命令。
- 承接 0017 尚未完成的构建发布环节，使产品稳定更新至七个公开模块目录；构建缓存、私有依赖不加入公开 PATH。
- 支持按模块构建，仅更新本次成功构建的产品；测试、检查或仅构建库不替换日常 CLI，失败保留原有可用程序。
- 将旧目录中的编译依赖、运行库、加载器和仍需使用的工具迁到仓库的私有产物区域，更新本机配置与相关路径元数据；保留计算节点所需兼容性。
- 校验 PATH 实际解析结果和新终端加载方式；清理 `~/.local/bin/` 中指向旧目录的 DFTFlow 入口，保留其他应用。
- 核验活动进程、排队任务、现用脚本与恢复记录；更新可迁移引用，保留历史证据，最后删除整个旧目录，不以同名链接或空壳继续保留。
- 退役或调整会重新创建旧安装的入口和文档，避免后续操作恢复双重安装。

## 范围外

- 外部 QE、VASP、Wannier90 等科学求解器及其安装路径。
- 科学参数、计算结果、预算和冻结回执的改写；不以更新路径或哈希伪造历史身份。
- 自动迁移其他项目、删除其他 `~/.local/share/` 内容或清空 `~/.local/bin/`。
- 在本次需求登记中执行目录删除、改动真实 shell 启动文件或提交科学作业。
- 线上 Issue 写操作、推送、创建或切换分支。

## 验收标准

- [ ] 全部九个产品与现有兼容命令从仓库外按名称解析至规范模块目录，实际启动成功；新终端、重复加载和带空格路径的行为通过验证。
