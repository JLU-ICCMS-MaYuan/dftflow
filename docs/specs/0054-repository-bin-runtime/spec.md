## 背景与目标

用户曾明确要求 DFTFlow 程序统一放到仓库根 `bin/` 的模块目录，并通过 PATH 在任意位置使用。0017 已完成 PATH 加载脚本，但构建仍输出到 Cargo 目录，发布到模块目录仍是独立操作。默认入口、仓库程序与最新构建可能来自不同版本。

本需求消除这一差异：交付构建完成后，PATH 指向的仓库产品即为本次版本；编译与运行依赖也不再留在即将删除的用户安装目录。

### 需求结论与变更取舍

保留 0017 的产品范围、模块映射及 PATH 加载能力，承接其尚未完成的自动发布环节。本次用户明确不再保留 `~/.local/share/dftflow/`，因此旧文档中“不改变 current 安装目的地”是历史基线，本次目标改为仓库唯一运行入口。

PATH 只负责查找已有文件，不会自动复制新构建，也不会解除 ELF 加载器和运行库依赖。自动发布、依赖迁移与实际命令来源验证均属于交付结果；不能只添加路径便宣称完成。

## 用户场景与验收

### US1：编译完成后直接使用新程序（P1）

用户通过受支持的交付构建入口编译全部产品或一个模块，成功后直接执行同名命令即可使用本次程序，不再手动复制或更新第二份安装。

**优先级理由**：解决本次“编译好之后就可以使用”的主要诉求。

**独立验收**：从旧产品状态进行完整构建和 EPW 模块构建，比较本次构建的来源记录与模块内制品；在仓库外运行对应命令。失败构建仍保留原有产品。

**验收场景**：

1. **假如**依赖齐备，**当**完整交付构建成功，**那么**本次产品及兼容入口稳定出现在仓库各模块目录，可按命令名运行。
2. **假如**只构建 EPW，**当**构建成功，**那么**三个 EPW 产品更新，无关模块保持原状。
3. **假如**构建、制品准备或启动验证失败，**当**构建入口返回失败，**那么**原有可用程序保持；测试或检查也不替换它们。

### US2：删除用户安装目录后仍能构建和运行（P1）

用户只在仓库维护产品与必要依赖，完整删除 `~/.local/share/dftflow/` 后仍能构建、更新和调用全部自有程序。

**优先级理由**：删除旧目录是用户明确要求，且现有程序存在实际依赖。

**独立验收**：迁移依赖和引用后，让旧路径不可访问，验证构建、九个产品启动和命令解析，再删除旧目录并重复核验。

**验收场景**：

1. **假如**程序或本机配置依赖旧目录，**当**迁移依赖并重新准备制品，**那么**它们不再通过加载器、RPATH、链接或构建元数据访问旧目录。
2. **假如**待删除目录仍有活动进程、排队作业或现用恢复引用，**当**迁移预检运行，**那么**列出具体引用及处理结果，完成相应迁移或任务结束前不执行删除。
3. **假如**依赖迁移与验证通过，**当**删除旧目录并再次构建和使用程序，**那么**目录不再存在，也不被重新创建。

### US3：从任意目录稳定调用仓库版本（P1）

用户在当前终端、新终端和受支持批处理环境中明确加载仓库环境后，同名命令均选中对应模块下的程序；旧用户入口不再遮挡。

**优先级理由**：否则自动更新的程序仍可能不是用户实际运行的版本。

**独立验收**：在 Bash/Zsh 中加载环境、重复加载、切换仓库外目录，核对全部公开入口；验证新终端配置步骤及含空格路径。

**验收场景**：

1. **假如**存在旧用户入口，**当**迁移并加载仓库环境，**那么**公开命令解析到模块目录，旧目录链接已清理，其他应用入口保持。
2. **假如**用户按说明配置新终端，**当**新终端加载环境，**那么**命令仍解析到仓库，重复加载不重复添加目录。

### 边界与异常场景

- 未编译的模块应明确缺失，不静默回退到旧安装；不能把其他模块的旧文件登记为本次构建结果。
- 发布时正在运行的程序、活动脚本与恢复身份须先核对；不通过覆盖历史回执或重算哈希绕过绑定。
- 旧路径仅出现在冻结历史证据中时，保留原始内容并说明历史执行依赖，不将其误判为需要改写的活动引用。
- 清理仅限确定归属本项目的旧根目录及入口，不删除其他用户软件或科学数据；未知目录内容先查明归属。
- 登录节点启动成功不等于计算节点兼容；后者须通过适合目标环境的受控启动或等效加载器验证，不执行真实科学计算。

## 功能需求

- **FR-001**：全部 DFTFlow 日常产品必须位于仓库 `bin/<模块>/`。模块映射沿用 0017：EPW 三程序、qeflow、vaspflow、wannier90、substitution、scflow 和独立 qf-gen-dyn0，共九个产品；兼容入口在相应模块内。
- **FR-002**：受支持的交付构建入口必须在成功返回前完成本次目标所需的运行制品准备和模块目录更新，使用户无需再执行安装命令即可使用本次版本；至少覆盖默认完整构建、EPW 按模块构建和独立工具构建。
- **FR-003**：只更新本次成功构建的产品。构建、依赖准备或启动预检失败不替换原可用程序；测试、检查和仅构建库的操作不发布 CLI。重复构建覆盖稳定路径，不产生另一套日常版本目录。
- **FR-004**：迁移旧根目录中仍需使用的编译依赖、运行库、加载器与工具；必要私有产物归仓库管理。更新本机配置、依赖元数据和制品引用，使后续构建与运行不再依赖旧根目录。
- **FR-005**：保留平台差异与目标计算环境兼容性；不得把尚未完成必要打包的原始产物直接当作日常可用版本发布。私有缓存和运行库不加入公开产品 PATH。
- **FR-006**：公开命令实际解析至仓库模块目录；提供当前终端、新终端和批处理加载方式，支持重复加载与含空格路径。清理 `~/.local/bin/` 中指向旧根目录的本项目入口，保留其他应用；不在本轮文档登记中改写真实 shell 启动文件。
- **FR-007**：删除前核验活动进程、调度器任务、现用脚本及恢复引用，并处理活动依赖。迁移与验证完成后完整删除 `~/.local/share/dftflow/`，不保留同名兼容链接、空壳目录或另一份该路径下的安装。
- **FR-008**：更新或退役仍会重新创建旧根目录的构建、打包、安装与工具操作，更新本机配置；正常构建、测试和运行不会重建它。
- **FR-009**：历史脚本、计算输出与身份记录保持可核验。对仍绑定旧执行程序的工作区明确支持的迁移或新尝试路径，不能修改旧身份冒充原执行；不删除外部求解器或科学数据。
- **FR-010**：同步根 README、模块与独立工具说明、测试指南、0017/0011 的后续关系及 Overview，以实际完成的构建与运行方式为准，并记录各项验收证据。

### 关键实体

- **产品与兼容入口**：唯一产品清单、家族归属、构建来源和实际命令解析结果。
- **私有依赖**：编译开发文件、运行库与加载器、相关路径元数据，不是公开 CLI。
- **迁移清单**：旧文件的归属、用途、活动引用、替代位置与核验结果；历史证据另保留。
- **发布证据**：本次构建目标、制品来源、兼容准备、启动核验及发布后身份。

## 成功标准

- **SC-001**：完整交付构建覆盖主 workspace 八个产品，独立工具构建覆盖第九个；无需另行安装即可从七个模块目录实际运行（FR-001/002）。
- **SC-002**：一次 EPW 模块交付构建仅更新对应三个产品；受控构建或预检失败时原产品哈希不变，测试和检查不发布；连续两次成功构建的公开相对路径集合一致（FR-003）。
- **SC-003**：旧根路径不可访问时，所需本机依赖检查、构建、增量更新及九个产品启动通过；加载器、RPATH 和活动构建配置均不引用旧根，目标计算环境兼容验证通过（FR-004/005）。
- **SC-004**：全部自有公开入口在仓库外的 Bash/Zsh 中解析到规范模块目录，当前终端与新终端加载步骤通过；重复加载路径不增长，含空格路径通过（FR-006）。
- **SC-005**：迁移清单逐项记录活动引用处理结果，现场冻结脚本和历史回执哈希不变；仍需使用的工作区有明确且经过针对性验证的后续使用路径（FR-007/009）。
- **SC-006**：旧根目录完整删除，原有指向它的自有入口已清理；再次构建、测试及相关工具启动不重建该目录（FR-007/008）。
- **SC-007**：文档与实际命令一致，需求、设计、技术任务和验证证据可追踪；不把源码完成或本地记录等同于线上关闭（FR-010）。
